## 2023-10-27 - Preventing Command/Option Injection in ssh invocation
**Vulnerability:** Invoking `ssh` externally using `std::process::Command` without using `--` to separate options from targets can allow users to inject arbitrary options (like `-o ProxyCommand="..."`) into the SSH invocation if the target string (e.g. username or hostname) starts with a hyphen.
**Learning:** Always use `--` argument separators when constructing external commands with user-provided arguments, even if the arguments are validated, as an extra layer of defense (Defense in Depth). Also, strictly validate that user inputs don't start with hyphens where applicable.
**Prevention:** Use `--` before the target argument when spawning the SSH process to prevent it from being parsed as an option.
## 2026-09-24 - Frontend-to-Tauri IPC Boundary Audit
**Vulnerability:** No new input-validation or injection issues found in the targeted scope. One known, still-open exception: credential writes are not serialized with master-password rekeying. `add_credential`/`update_credential` don't check `changing_password`, so a write that lands during `change_master_password`'s re-encryption transaction or its post-commit key-swap window is encrypted with the old key and becomes undecryptable under the new one (see `AGENTS.md`, "Deferred Bug-Audit Fixes: Status Reconciliation"). This audit does not close that finding.
**Learning:** Conducted a focused security audit of the frontend-to-Tauri IPC boundary, specifically looking for any command that accepts untrusted UI data and can read/write sensitive state without the expected validation or vault-state check. Reviewed critical commands like `add_credential`, `update_credential`, `export_database`, `import_database`, `scan_network`, `add_scheduled_task`, `update_scheduled_task`, and SSH/Terminal launching commands. The codebase demonstrates a robust defense-in-depth approach at this boundary. Inputs are strictly validated using functions from `validation.rs` (e.g., `validate_ip`, `validate_hostname`, `validate_username`, `validate_port`, `validate_path`, `validate_cidr`). State access checks (e.g., requiring `master_key` to decrypt/encrypt vault items) are consistently enforced, with the rekeying race above as the exception: holding *a* master key is checked, holding the *current* one is not. Safe APIs like `rusqlite::params!` and `rusqlite::backup::Backup` prevent SQL injection and unsafe file operations. Process execution (`Command::new`) defends against option injection using `--`. Unvalidated fields like `credential_type` or `model` do not cross into unsafe behavior or memory corruption.
**Prevention:** Maintain the current practice of strictly validating all incoming IPC payload fields and utilizing safe frameworks/APIs before acting on untrusted data.
