# Phase 5: Tests, dependencies, CI/release

Date: 2026-09-24 · Audited commit: `97dd84a` (master). The working tree HEAD moved to audit-doc-only commits after that, and `git diff 97dd84a HEAD -- src src-tauri .github package.json` is empty.
Linear: EDW-23. Baseline data (coverage, `cargo test`, `cargo audit`, `cargo deny`, `cargo tree -d`, outdated lists) came from `fcc58d2` / `75a6ca8` (`audit/raw/`, `audit/coverage-fe/coverage-summary.json`). Where 97dd84a changed a file (vault.rs, lib.rs, scheduler.rs, four frontend files), I re-read the current code. The EDW-15 regression test is new in 97dd84a, so it isn't in the baseline `cargo-test.txt`.

**Threat model.** This is a single-user desktop app. The realistic attackers are (a) a malicious or compromised SSH server or LAN peer, (b) a compromised webview calling IPC commands, and (c) the software supply chain (dependencies, CI actions, the release pipeline that signs auto-updates). A local attacker who already has code execution is out of scope, per SECURITY.md. Severity is calibrated to that: a crash of an optional feature is Low, not High.

## Scope & method

- **Test gaps.** I ranked files by `audit/raw/cargo-llvm-cov.txt` (Rust per-file lines/functions) and `audit/raw/vitest-coverage-retry.txt` + `coverage-summary.json` (FE), then read the untested code on the critical paths: vault KDF/rekey (`vault.rs`), host-key verification (`ssh.rs`, `ssh_exec.rs`, `sftp.rs`, `vault/ssh_keys.rs`), `ssh_auth.rs`, `scheduler.rs`, DB import/export (`lib.rs`), and command-boundary validation. For every one of the 73 IPC commands I checked whether any FE test names it (`grep` over `*.test.ts*`) and whether any Rust test reaches its logic (from the `cargo-test.txt` test list plus the coverage data).
- **EDW-15 regression test.** I read `vault::tests::test_credential_write_waits_for_master_password_change` (`vault.rs:1075–1175`) against `change_master_password` / `credential_access` (`vault.rs:477–500, 538–730`) and reasoned through how the runtime schedules it under three mutations. Nothing was run, because the preamble forbids compiling.
- **Test quality.** A script over all 351 FE test blocks flagged blocks with no `expect`, or whose only `expect`s are on mocks/`invoke`. I also grepped Rust tests for empty or tautological bodies and for `sleep`/timers. For contract drift, I compared a sample of Rust command signatures and return structs against their FE `invoke` payloads, TS interfaces and test mocks: 16 commands, plus the structs `SshHostKey`, `CredentialSummary`, `CredentialFrontendView`, `ScheduledTask`, `SavedHost`, `TunnelInfo`, `AuditLogEntry`, `RemoteFile`, `AlertRule` + enums, `AppInfo`, `HostKeyVerificationResult`, and the `ssh-host-key-verification` event.
- **Dependencies.** Inputs were `npm-outdated.txt`, `cargo-outdated.txt`, `cargo-audit*.txt` (JSON settings plus warnings), `cargo-deny-full.txt` (grepped for advisory and license sections) and `cargo-tree-dups.txt`. I ran read-only `cargo tree --locked -i <crate> [-e features]`. It fetched the index and crate sources into `~/.cargo`, and the repo is unchanged (`git status` clean). I read the dependency source in `~/.cargo/registry/src` for russh 0.62.7 (kex modules, rsa usage), ssh-key 0.7.0-rc.11 (RSA signing), rsa 0.10.0-rc.18 (blinding), mdns-sd 0.20.3 (`read_char_string`), and the Tauri Linux stack (`VariantStrIter` users). Changelogs came from raw GitHub (argon2, password-hash, chacha20, mdns-sd) and the crates.io API (versions/yanks). I ran `npm view` for vitest 5. The GitHub API for third-party repos was blocked, so the russh / russh-sftp / dns-lookup / vitest 5 changelogs are **UNVERIFIED**.
- **CI/release.** I read `.github/workflows/ci.yml`, `release.yml`, `docs/RELEASE_SIGNING.md`, `src-tauri/.cargo/audit.toml`, `package.json`, `package-lock.json`, `Cargo.toml`, `Cargo.lock` and `tauri.conf.json`. I used GitHub Actions run history (read-only MCP: `list_workflow_runs`, `list_workflow_jobs`, `list_tags`) to confirm what actually runs.
- **Not run:** `npx knip` and `gitleaks`. Neither applies to this phase's scope, and there's no `node_modules`.

### Rekey regression test verdict (EDW-15, TEST-008)

`vault::tests::test_credential_write_waits_for_master_password_change` (`vault.rs:1075-1175`):

1. **Does it force the interleaving?** Yes. `#[tokio::test]` defaults to the current-thread runtime, so spawned tasks run only when the test yields. The test holds a real `credential_access()` read guard (`:1099`), spawns the rotation, and polls `credential_gate.try_read()` for up to 1000 yields until the rotation is queued as a writer (tokio's `RwLock` is fair, so a queued writer blocks new readers). It then spawns the writer and yields 50 times while asserting `!writer.is_finished()`. Both waits are bounded, so a mutant fails the test instead of hanging it. Nothing depends on wall-clock timing.
2. **Mutation: remove `write_owned()` from `change_master_password` (`:551`).** `try_read` never fails, and the assert at `:1115` fires. **Caught.**
3. **Mutation: remove the gate from `credential_access` (`:491`).** `in_flight` holds nothing, so the rotation takes the gate and `inner` uncontended, sets `changing_password = true`, and parks in `spawn_blocking`. The loop breaks, and the assert at `:1119` (`!changing_password`) fires. **Caught.**
4. **Mutation: release the gate before installing the new key** (e.g. `drop(_credential_gate)` just before `self.inner.write().await` at `:720`). The writer is woken, but the rotation task keeps running: `inner.write()` is uncontended and completes without yielding, so the key is swapped before the writer ever runs. `write_key == new_key`. **Not caught.**
5. **Call sites:** the test never goes through `lib.rs`/`scheduler.rs`, so a call site reverting to `get_master_key()` isn't caught (TEST-002). Making `get_master_key` private closes that at compile time.

**Test to add (`vault::tests::test_gate_held_until_new_key_installed`):** initialize the vault, record the initial `master_password_hash` from `vault_settings`, and spawn `change_master_password`. Poll (bounded, `yield_now` + 10 ms sleeps, up to 30 s) until the rotation sets `changing_password == true`. Then take and **hold** `let g = vault.inner.read().await`. Poll the DB (a separate `db::open_connection`) until `master_password_hash` differs from the initial value, which means the commit is done. Yield 50 times so the rotation reaches its final `inner.write()` and blocks on `g`. Assert `vault.credential_gate.try_read().is_err()` (the gate is still exclusively held across the swap). Drop `g`, await the rotation, then assert `credential_access().await.unwrap().key() == get_master_key()`. Mutation 4 makes `try_read()` succeed and fails the test. The test is deterministic because the swap can't complete while the test holds `inner`.

### RSA / Dependabot alert #1 verdict (EDW-16, DEP-005)

- **Identity:** `rsa 0.10.0-rc.18` (`Cargo.lock:400`) ← `russh 0.62.7` (unconditional dependency) and ← `ssh-key 0.7.0-rc.11` (feature `rsa`, enabled by russh's `rsa` feature, which Quasar turns on in `Cargo.toml`). Source: `cargo tree --locked -i rsa -e normal,features`. It's the only vulnerability `cargo audit` finds (`vulnerabilities.count = 0` after the `audit.toml` ignore; the baseline JSON shows `settings.ignore = ["RUSTSEC-2023-0071"]`). The attribution to Dependabot #1 is consistent, but the alert itself wasn't readable here (UNVERIFIED, as in CLAUDE.md).
- **Decryption oracle (the Marvin attack proper): not present.** russh's kex modules are `curve25519`, `dh`, `ecdh_nistp`, `hybrid_mlkem` and `none` (`russh-0.62.7/src/kex/`). There's no RFC 4432 RSA key exchange, so the client never RSA-decrypts anything. The only `rsa::` uses in russh are key parsing (`keys/format/pkcs8.rs:50-56, 246`, `keys/format/mod.rs:151`). Encrypted private keys are decrypted with bcrypt-pbkdf plus symmetric ciphers (ssh-cipher), not RSA.
- **Private-key operation that is reachable: RSA signing** in publickey auth (`ssh_auth.rs:80-88`, used by the terminal, exec, pool, tunnel and monitoring paths), whenever the user stores an RSA key. That path is **unblinded**: ssh-key calls `rsa::pkcs1v15::SigningKey::try_sign` (`ssh-key/src/signature.rs:706-715`), which calls `sign::<DummyRng>(None, …)` (`rsa-0.10.0-rc.18/src/pkcs1v15/signing_key.rs:182-194`). The modular exponentiation is crypto-bigint Montgomery `pow` (`src/algorithms/rsa.rs:64-69`), which is constant-time in the exponent. The advisory now says what remains is padding (decryption) and default-path blinding.
- **Who could measure it:** only the SSH server the user is authenticating to. It would get one signature per new connection, over network jitter, and `ssh_pool` reuses sessions. That server is already the relying party for the key.
- **Verdict:** the advisory's attack isn't reachable. The residual signing-timing exposure is theoretical, so it's Info. The SECURITY.md/`audit.toml` rationale ("signs, doesn't decrypt") is correct. One refinement: note that signing is unblinded in rsa 0.10-rc but uses constant-time modexp. Dismissal in the GitHub UI is justified.
