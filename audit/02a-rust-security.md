# Phase 2A — Rust security audit

Date: 2026-09-24 · Audited commit: `97dd84a` (working tree HEAD `6665448` is a merge. `git diff --stat 97dd84a HEAD -- src-tauri src` is empty, so the source is identical.)
Baseline data (build/test/clippy/coverage/cargo-audit) comes from `audit/raw/` at `fcc58d2`. Nothing was compiled or run for this phase.
Linear: EDW-19. Finding prefix: `RSEC-`.

## Threat model used

This is a single-user desktop app, so the attackers considered are:

1. Anyone who gets **read access to `quasar.db`** or a copy of it: another local user, malware running as a different user, a cloud or home-directory backup, a stolen laptop disk, a DB export, or the `quasar.db.bak` file.
2. A **malicious network or remote host**: MITM on SSH, hostile SSH/SFTP servers, and hostile mDNS/Tailscale names.
3. A **compromised webview**, i.e. XSS that can call any registered Tauri command. Whether XSS is reachable is Phase 2B's question; here I only rate what such a webview could do through Rust.

Severity is calibrated to that model. Findings that only matter under (3) are capped at Medium.

## Scope & method

- **Read in full:** `vault.rs`, `vault/credentials.rs`, `vault/ssh_keys.rs` (verify/trust paths), `crypto.rs`, `ssh.rs` (handler, connect, IPC), `ssh_auth.rs`, `ssh_tunnel.rs`, `launcher.rs`, `ai.rs`, `health.rs`, `db.rs`, `errors.rs`, and `lib.rs` lines 1–1850 (every command body, including export/import and the auto-lock and SSH-idle loops).
- **Read in part:** `scheduler.rs` (credential resolution, task execution, due-task runner), `ssh_exec.rs`, `ssh_pool.rs`, `sftp.rs`, `tailscale.rs`, `scanner.rs`, `validation.rs`.
- **Rekey race (EDW-15):** grepped every `get_master_key` / `credential_access()` / `credential_gate()` / `CredentialManager::{add,get,update,delete}_credential` call site, plus any SQL touching `credentials` or `vault_settings` outside the vault modules (none). Traced the lock order and each interleaving by hand.
- **Argon2 salt/key handling:** downloaded the `argon2-0.5.3` crate source (the locked version) into the scratchpad and read `PasswordHasher::hash_password` (`src/lib.rs:572-597`) to confirm how it uses the salt.
- **Commands and processes:** grepped for `Command::new|process::Command|.arg(|.args(`. There are three spawn sites.
- **SQL:** grepped for `format!` into SQL strings and for `push_str` query builders.
- **Logging:** grepped for `println!/eprintln!/dbg!`, the log macros, and `{:?}`.
- **Frontend (read only where the Rust behaviour depends on it):** `useSshHostKeyVerification.ts`, `SshHostKeyPrompt.tsx`, `VaultSettings.tsx`, `SystemHealthWidget.tsx`, `MonitoringView.tsx`, `useViewVisibility.tsx`, `Layout.tsx`, `AIAssistant.tsx`.
- **Updater:** `tauri.conf.json` plugin block (decoded the pubkey header), `capabilities/default.json`, `useUpdater.ts`.
- **Tools:** `gitleaks` and `knip` were not run. Neither is installed and neither is needed for Rust security review.

## Checked and clean

- **EDW-15 rekey race: the fix is in place (by code inspection; not compiled or run).** Every credential encrypt/decrypt path goes through `VaultState::credential_access()`: `connect_ssh` (`lib.rs:221`), `start_ssh_tunnel` (`:286`), `get_remote_hosts_health` (`:998`), `add_credential` (`:1266`), `get_credential` (`:1293`), `reveal_credential_password` (`:1309`), `update_credential` (`:1350`) and `scheduler::resolve_cred_for_task` (`scheduler.rs:373`). `delete_credential` takes `credential_gate()` (`lib.rs:1378`).
  - The only caller of `get_master_key()` outside tests is `credential_access` itself (`vault.rs:492`).
  - No SQL touches `credentials`/`vault_settings` outside `vault.rs`/`vault/credentials.rs`.
  - `change_master_password` takes `credential_gate.write_owned()` first (`vault.rs:551`), before it reads `inner` or sets the flag, and holds it past the key install (`:720-739`).
  - Lock order is gate → `inner` everywhere. `unlock_vault`, `lock_vault` and `check_auto_lock` touch only `inner`, and no path takes the gate twice, so there's no deadlock against tokio's write-preferring `RwLock`.
  - The `CredentialAccess` is dropped before the network phase in `connect_ssh` (`:228`), `start_ssh_tunnel` (`:293`) and `get_remote_hosts_health` (`:1015`). In the scheduler it goes out of scope at the end of the `if let` block.
  - `lock_vault` mid-rotation is respected (`:733`). Auto-lock mid-rotation is suppressed by `changing_password` (`:454`).
  - Lock → unlock-with-old-password mid-rotation still ends with the new key installed, consistent with the committed hash.
  - `export_database` during a rotation uses the backup API, which gives a consistent pre- or post-commit snapshot.
  - **Remaining gap:** `import_database` (RSEC-004). A regression test exists (`vault.rs:1076`), but it was added after the `fcc58d2` baseline, so the baseline run doesn't show that it passes.
- **Argon2id and nonce parameters:** Argon2id v0x13 with m=47104 KiB, t=2, p=1 (OWASP), a 16-byte `getrandom` salt (`crypto.rs:12-16`) and a 12-character master-password minimum enforced both at the command and in `VaultState`. The key-derivation problem is the salt/output reuse in RSEC-001, not the parameters.
- **AES-GCM nonces:** a fresh 96-bit `getrandom` nonce for every encrypt call and every field (`crypto.rs:49-53`). Nonce and tag lengths are checked on read (`credentials.rs:121,249-267`). Volume is far below the random-nonce bound, so there's no reuse path.
- **Constant-time comparisons:** password verification uses `argon2::PasswordVerifier` (constant-time output compare). The host-key fingerprint compare uses `subtle::ct_eq` (`ssh_keys.rs:127-131`), which is unnecessary for public data but harmless.
- **Lockout:** persisted and escalating (`vault.rs:240-306,361-384`). It only matters for an online attacker (see RSEC-001).
- **Host key checks on every SSH path.** There are five `client::Handler` impls, and all of them verify:
  - `ssh.rs:63`, used by the terminal and tunnels: prompts with a UUID `requestId`, defaults to reject after a 120 s timeout, and cancels the pending request.
  - `ssh_exec.rs:30`, used by one-shot exec, `ssh_pool`, `health`/monitoring and scheduled SSH tasks: only `Trusted` keys pass; anything else is `Disconnect`.
  - `sftp.rs:34`: only `Trusted` keys pass.
  - `ssh_connect.rs:107` and `ssh_pool.rs:372`: `#[cfg(test)]` handlers only.
  - The pooled and scheduled paths do check host keys. They verify at session establishment, and `MAX_LIFETIME` 30 min forces re-verification (`ssh_pool.rs:30-33`).
  - The frontend doesn't auto-approve: approval happens only in the `SshHostKeyPrompt` click handlers. A compromised webview can approve, which is inherent (RSEC-006 covers the part that is fixable).
- **Agent forwarding:** hard-coded `false` (`lib.rs:254`). No other caller passes `true`.
- **Tunnels:** bind to `127.0.0.1:{local_port}` (`ssh_tunnel.rs:185`), not `0.0.0.0`. Host and port are validated.
- **Process spawning** (only three sites):
  - `launcher.rs`: SSH via `cmd /C start ssh -- user@host` on Windows, `open ssh://` on macOS, and `<term> -e ssh -- target` on Linux. RDP via `mstsc /v`.
  - All inputs pass `validate_ip|validate_hostname` and `validate_username` (`lib.rs:348-353,359`), whose regexes (`validation.rs`) allow only `[A-Za-z0-9._-]`. That rules out cmd.exe metacharacters, spaces, quotes and `=`, and `--` blocks option injection.
  - `launch_ssh_external` is never invoked by the frontend (recon §3.2).
  - `tailscale.rs:162` runs with fixed args and no shell.
- **Scanner:** the CIDR regex, plus a `/16` maximum (65,536 addresses, `scanner.rs:82-88`) and 50-way concurrency. There is no huge-range DoS.
- **SQL injection:** every query is parameterised. The only `format!`-built SQL is `PRAGMA table_info({})`, which is called with literal table names only (`lib.rs:141,154-169`), and the `IN (?,?,…)` placeholder list (`lib.rs:716-717`). The audit and host-search `LIKE` patterns are bound parameters. `export_database` uses the backup API, not `VACUUM INTO` string interpolation (`lib.rs:1712-1722`).
- **Ollama / AI:**
  - Uses `Ollama::default()` (localhost). The context `AIAssistant.tsx:63-111` sends discovered-host IPs, hostnames, vendors and services plus saved-host name, address, protocol and port. It sends **no usernames, credential ids or secrets**, and no remote command output.
  - Model output is rendered as text (`whitespace-pre-wrap`, React-escaped) and there is no tool or action path. Prompt injection through mDNS or host names can therefore only affect the chat text.
- **Updater:**
  - The minisign pubkey is embedded (key id `C8941F23EE6A80DA`) and there is a single HTTPS endpoint (`github.com/shingoku2/quasar/releases/latest/download/latest.json`).
  - There are no `dangerous*`, insecure-transport or downgrade options in the config or in `useUpdater.ts`.
  - The plugin enforces signature verification against the embedded key, so a MITM or a swapped `latest.json` can't install an unsigned build.
- **Logging:**
  - There is no `println!`/`dbg!` in production code (only in the `ssh_pool` bench test).
  - `env_logger` is active only with `RUST_LOG` set.
  - No log statement formats a password, key or passphrase. `ssh_auth` logs only parse or IO errors, not key contents.
  - `security_audit_log.details` is always `None` at every call site.
  - `sanitize_error` keeps internals out of the UI; interactive SSH connect errors are verbose by design.
- **Accepted risk:** RUSTSEC-2023-0071 (`rsa`, Marvin) is ignored in `.cargo/audit.toml` and documented in `SECURITY.md`. It is only reachable through client-side RSA signing with user RSA keys, so the accepted-risk rating is reasonable.

## UNVERIFIED / needs follow-up

- **RSEC-001 hasn't been observed at runtime.** The conclusion comes from the argon2 0.5.3 source and identical call parameters. No toolchain or Python argon2 was available to run it. A five-line test (`assert_ne!(PasswordHash::new(&stored).hash.as_bytes(), vault.get_master_key())`, which currently would fail) would confirm it in CI.
- **The EDW-15 regression test's pass/fail isn't known.** `vault::tests::test_credential_write_waits_for_master_password_change` postdates the baseline test run and couldn't be compiled here.
- **Key-schedule zeroisation isn't checked.** Whether `aes`/`aes-gcm 0.11` are built with the `zeroize` feature (which wipes expanded round keys) wasn't checked, because `cargo tree -e features` needs the registry.
- **russh 0.62 default algorithm lists weren't reviewed** (whether `ssh-rsa`/SHA-1 host keys and non-ETM MACs are accepted), since the crate source isn't vendored.
- **Copies from converting IPC-deserialised `String` to `SecretString` aren't assessed.** `SecretString::from(String)` may reallocate, and the serde and IPC buffers can't be zeroised. This is inherent to Tauri IPC.
- **File permissions on Windows and macOS** (RSEC-009) weren't assessed, only the Unix umask default.
- **Whether the compromised-webview findings are reachable at all** (RSEC-005/006, and parts of 008 and 013) depends on XSS reachability, for example mDNS, Tailscale or remote hostnames rendered into the DOM. That is Phase 2B.
